Choose the function for your task

This is a task-oriented guide, not a replacement for help() in the installed package. The tutorials validate the particular code paths shown with fastQR 1.1.6.

1 Reading an interface in context

A function name identifies an interface, but the matrix being factorized and the information returned still depend on the task. An explicit decomposition of X supplies factors that reconstruct that design. A compact decomposition stores transformations defining the orthogonal factor. A regression routine uses such calculations within a model-fitting procedure and can return factors of a working system instead of the original design.

This distinction is particularly relevant for ridge. With type = "QR", the returned Q and R factorize the normalized penalized system. With type = "R", the triangular factor comes from an augmented design and satisfies a different cross-product identity. The coefficient vectors solve the same normalized ridge problem, but their intermediate factors should not be interchanged as though they described the same matrix.

2 Decomposition and extraction

Function Purpose
qr() Explicit full or thin QR factors
qr_thin() Thin-factor interface; consult its help for input conventions
qr_fast() Compact Householder representation, optionally pivoted
qr_Q(), qr_R() Extract factors from compact output
qr_Q_full(), qr_Q_reduced2full() Form or complete an orthogonal factor
qr_X() Reconstruct the design from a factorization
qr_pivot2perm() Convert pivot information to a permutation matrix
qrchol(), rchol() Obtain a triangular Gram factor

For a tall design, the upper triangular part of the leading square block in qr_fast() output contains R. Entries below the diagonal store Householder-vector information, while qraux stores the corresponding transformation coefficients. Those entries are part of a compact representation, rather than a reconstruction error left below the triangle. The extraction helpers interpret that storage and apply the transformations when explicit factors are needed.

The decomposition tutorial explains the permutation convention. Use fastQR::qr() and base::qr() explicitly when comparing implementations.

3 Change the design

Function Purpose Example
qrupdate() Insert rows or columns in a QR factorization Insert observations
qrdowndate() Delete consecutive rows or columns Delete predictors
rupdate() Update only the triangular factor R-only updating
rdowndate() Downdate only the triangular factor Sliding-window regression

For row batches, the examples supply a p by m matrix, with each new observation stored in a column. QR insertion uses a one-based position. R-only insertion of predictors appends columns to the right.

The orientation follows the algebra. A batch of new observations contributes U %*% t(U) to the predictor cross-product matrix, whereas new predictor columns require cross-products with the existing observations. For an R-only row deletion, the values of the removed observations are supplied because their contributions must be subtracted. For a QR deletion by position, the current complete factors also encode the relevant observation geometry. These are different input conventions for related matrix operations.

4.1 Orthogonal transformations and coefficient coordinates

The products returned by qr_Qty() and qr_Qy() use the complete orthogonal transformation encoded by the compact factors. Their input vector has n entries, and their output also has n entries. For a tall full-column-rank design, the first p coordinates of the complete transformed response agree with the thin projection crossprod(Q1, y). A subsequent triangular solve is still required to obtain p regression coefficients.

The qr_lse_Qty() and qr_lse_Qy() helpers construct the factorization internally and apply the corresponding complete transformation. This separates multiplication by an orthogonal factor from projection onto a fitted column space: the least-squares fitted response uses both stages, Q1 transpose followed by Q1, while a coefficient vector uses the projection followed by the triangular solve. Keeping track of those dimensions makes the similarly named operations easier to distinguish.

4.2 Model specification and validation

The model-fitting functions receive numeric designs rather than formula objects. A column of ones must be supplied when an intercept is part of the design, and ridge penalizes that column unless the intercept is handled separately by centering. A fixed-penalty fit and a validation procedure are also different operations: the first estimates coefficients at a supplied value, while the second compares held-out prediction losses and then refits at a selected value.

Prediction designs must reproduce the training column definitions and ordering. When preprocessing is estimated from data, the transformation used for a validation observation must be learned from its training fold; the transformation for a final test prediction is learned from the complete training sample. The explicit validation loop illustrates these distinctions before the native CV interfaces are introduced.

4.3 Scope of the regression examples

The regression chapter checks both ridge backends and the univariate and multivariate cross-validation interfaces against independent augmented-design QR calculations. It also retains an explicit fold loop for examples that estimate centering and scaling within each training fold. These procedures have different preprocessing and intercept conventions; the distinction is explained before the native CV example.

help("qrupdate", package = "fastQR")
help("qrridge", package = "fastQR")

The positive-penalty ridge interfaces, including cross-validation, also accept more predictors than observations. See Ridge with growing designs for augmented-design updates and the distinction between fixed total and normalized penalties. Ordinary least-squares interfaces retain their full-column-rank restrictions.
